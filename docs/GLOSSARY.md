# AI Presentation Studio 小白词典

这是一份由 Agent 持续维护、面向第一次做软件项目的用户的可扩展词典。

你不需要把它背下来。遇到看不懂的词时，用编辑器搜索或按 `Ctrl + F` 查找中文、英文或缩写即可。Agent 在对话中第一次使用陌生术语时仍然应该直接解释，不能只把你丢到这份词典里。

## 这份词典和其他文档的区别

- [`CONTEXT.md`](../CONTEXT.md)：定义 AI Presentation Studio 自己的产品词语，例如“演示项目”“生成请求”“可编辑图片”。它是产品语言的正式依据。
- [`docs/adr/`](adr/)：记录难以反转的技术决定，以及为什么这样选。
- [正式 Spec Issue #1](https://github.com/breakoutmission/new-design/issues/1)：规定一周 MVP 要做什么、如何验收。
- 本词典：解释产品、设计、Git、AI、网页、测试和开发中会反复遇到的通用专业词。

维护规则见 [`docs/agents/glossary.md`](agents/glossary.md)。

## 第一次先认识这些词

如果你暂时不想看完整词典，先理解下面 12 个就足够继续当前项目：

| 词语 | 最短解释 |
| --- | --- |
| MVP | 最小但能完整展示核心价值的第一版，不是“随便做个残次品” |
| Spec / PRD | 开发前写清楚“做什么、为什么、怎样算完成”的正式说明 |
| Issue | Issue Tracker 中一件可以被跟踪的工作或问题 |
| ADR | 记录重要技术选择及其理由的小文档 |
| 原型 | 为了验证问题而制作的简化版本，不一定能直接成为正式产品 |
| 分支 | Git 中一条独立修改路线，可以不影响 `main` |
| Commit | 一次有说明、有编号的代码或文档存档 |
| Agent | 能读取上下文、使用工具并执行多步任务的 AI 助手 |
| Token | 模型读写内容时使用的计量单位，不等于汉字数或账单金额 |
| 前端 / 后端 | 用户看见和操作的部分 / 在背后处理数据和任务的部分 |
| 端到端测试 | 从用户入口走完整流程，确认各部分组合后仍然可用 |
| 验收标准 | 判断一项工作是否真正完成的可检查条件 |

## 一、产品规划与任务管理

### MVP（Minimum Viable Product，最小可行产品）

- **一句话**：功能尽量少，但必须能让目标用户完整体验核心价值的第一版产品。
- **在本项目中**：一周 MVP 要从双击启动走到生成、编辑、保存、重新打开和导出，而不是只做一个漂亮首页。
- **别混淆**：MVP 不是“质量可以很差”，而是“范围小、核心链路完整”。

### 范围（Scope）与范围外（Out of Scope）

- **一句话**：范围是这次确定要做的内容；范围外是明确决定暂时不做的内容。
- **在本项目中**：文字编辑和 PDF 导出属于范围；PPTX 导出、任意 HTML 导入和图片生成属于一周 MVP 的范围外。
- **为什么重要**：没有范围外清单，项目会不断加入新想法，最后什么都做不完。

### 需求（Requirement）

- **一句话**：产品必须满足的用户需要或行为条件。
- **在本项目中**：“点击保存后显示保存成功”是一条需求；“按钮使用某个内部函数”不是用户需求。

### Spec / PRD（Specification / Product Requirements Document，产品需求说明）

- **一句话**：开发前对问题、方案、用户故事、实现决定、测试和范围外内容的正式约定。
- **在本项目中**：GitHub Issue #1 是当前一周 MVP 的正式 Spec。
- **别混淆**：Spec 说明“要交付什么”；交接文档说明“当前做到哪里”。

### 用户故事（User Story）

- **一句话**：从用户角度描述“谁想做什么，以及为什么”。
- **常见格式**：作为某类用户，我希望完成某件事，从而获得某种好处。
- **例子**：作为首个用户，我希望保存后看到成功提示，从而确信修改没有丢失。

### 验收标准（Acceptance Criteria）

- **一句话**：可以实际检查的“完成条件”。
- **例子**：“导出 PDF”不够具体；“12 张幻灯片分别成为 12 张尺寸正确的 PDF 页面”才容易验收。
- **别混淆**：验收标准不是开发步骤，也不是“看起来差不多”。

### 里程碑（Milestone）

- **一句话**：项目推进到某个重要阶段的标志。
- **在本项目中**：技术链路跑通是一个里程碑；完成一周真实材料演示是下一个更大的里程碑。

### Issue（任务/问题单）

- **一句话**：Issue Tracker 中一件可以被编号、讨论、分配和关闭的工作或问题。
- **在本项目中**：Issue #1 承载正式 MVP Spec；后续子 Issues 承载具体开发链路。

### Issue Tracker（任务跟踪系统）

- **一句话**：集中管理 Issue、状态、负责人和讨论的位置。
- **在本项目中**：配置好的 Issue Tracker 是 GitHub Issues。

### Label（标签）与 Triage（分诊）

- **一句话**：标签说明 Issue 当前需要什么；分诊是判断它应进入什么状态的过程。
- **在本项目中**：`needs-info` 表示还缺信息，`ready-for-agent` 表示已经足够清楚，可以由 Agent 执行。
- **类比**：像医院先判断患者该去哪个科室，而不是立刻开始治疗。

### 父 Issue、子 Issue 与依赖（Parent / Child / Dependency）

- **一句话**：父 Issue 描述较大的目标，子 Issue 是其中一块可完成工作；依赖表示一项工作必须等另一项先完成。
- **例子**：“导出 PDF”可能依赖“项目已经可以保存和重新打开”。
- **常见写法**：`Part of #1` 表示属于 Issue #1；`Blocked by #2` 表示被 Issue #2 阻塞。

### 纵向切片（Vertical Slice / Tracer Bullet）

- **一句话**：一次完成一条从界面到后端、可以独立演示的小链路。
- **在本项目中**：“首页 → 新建 → 选 Grove → 发送 → 进入预览”是一条纵向切片。
- **别混淆**：先把所有页面画完、再把所有后端写完是横向分层，早期很难证明整体真的能跑。

### ADR（Architecture Decision Record，架构决策记录）

- **一句话**：记录一个重要技术决定、备选方案和选择理由的小文档。
- **什么时候需要**：决定难以反转、未来读者会疑惑、并且确实存在取舍时。
- **例子**：首周使用完整 HTML，虽然 Token 较多，但最快能交付演示；这值得写 ADR。

### Handoff（交接）

- **一句话**：让没有上下文的新 Agent 或新成员知道当前状态、下一步和风险的文件。
- **在本项目中**：仓库根目录的 `handoff.md` 与 Windows 临时目录中的 `new-design-handoff.md` 保存相同的当前接手信息，下一任务开始前应先阅读。
- **别混淆**：Handoff 不是 Spec，不应重新定义产品需求。

## 二、原型与界面设计

### 原型（Prototype）

- **一句话**：为了回答一个问题而制作的简化版本。
- **例子**：原型可能只证明“图片能不能在 GrapesJS 中拖动”，并不包含完整首页和错误处理。
- **别混淆**：原型验证方向，正式产品承担长期使用和维护。

### 技术原型（Technical Prototype）

- **一句话**：验证技术组合能否工作的原型。
- **在本项目中**：现有 Open Design + Codex + GrapesJS 原型证明生成、编辑、保存和导出链路可行。

### 交互原型（Interaction Prototype）

- **一句话**：验证用户看见哪些页面、点击后发生什么、状态怎样变化的原型。
- **在本项目中**：首页、新建项目、生成中、预览、编辑和失败状态仍需要低保真交互原型。

### 低保真与高保真（Low-fidelity / High-fidelity）

- **一句话**：低保真先确认结构和流程；高保真更接近最终颜色、字体、间距和视觉效果。
- **类比**：低保真像房子的平面草图，高保真像装修效果图。
- **当前建议**：一周 MVP 先做低保真，不要过早花时间抛光视觉。

### 线框图（Wireframe）

- **一句话**：用方框、文字和简单控件表示页面结构的草图。
- **别混淆**：线框图重点是信息放在哪里，不是最终视觉设计。

### 用户流程（User Flow）

- **一句话**：用户为了完成目标会依次经过哪些页面、状态和操作。
- **例子**：首页 → 新建 → 粘贴材料 → 选择模板 → 发送 → 预览 → 编辑 → 保存 → 导出。

### 正常路径与异常路径（Happy Path / Error Path）

- **一句话**：正常路径描述一切顺利时的流程；异常路径描述失败、取消、输入错误或权限问题时怎样恢复。
- **在本项目中**：Codex 生成成功是正常路径；生成失败后保留材料并允许重试是异常路径。

### UI 与 UX（User Interface / User Experience）

- **一句话**：UI 是用户看见和点击的界面；UX 是完成任务时整体是否清楚、顺畅和可信。
- **例子**：漂亮按钮属于 UI；保存后明确告诉用户成功，属于 UX。

### 页面与状态（Page / State）

- **一句话**：页面是一个主要界面；状态是同一页面在不同情况下显示的样子。
- **例子**：“项目工作区”是页面；生成中、预览、编辑、失败和已取消是这个页面的不同状态。

### 弹窗、对话框与 Toast（Modal / Dialog / Toast）

- **一句话**：弹窗或对话框要求用户先做决定；Toast 是短暂出现、不阻塞操作的提示。
- **例子**：删除项目需要确认对话框；“保存成功”适合使用 Toast。

## 三、Git 与 GitHub

### Git

- **一句话**：记录文件历史、比较变化和管理多条修改路线的版本控制工具。
- **类比**：像带时间线、备注和分支能力的超级存档系统。

### Repository / Repo（仓库）

- **一句话**：由 Git 管理的一整个项目目录及其历史记录。
- **在本项目中**：本地仓库位于 `G:\AITOOLS\NEW-DESIGN`，远程仓库位于 GitHub。

### Local 与 Remote（本地与远程）

- **一句话**：Local 是当前电脑上的仓库；Remote 是 GitHub 等服务器上的仓库副本。
- **别混淆**：本地 Commit 不会自动出现在 GitHub，必须 Push。

### origin 与 Tracking Branch（远程仓库名与跟踪分支）

- **一句话**：`origin` 通常是当前 GitHub 远程仓库的简称；跟踪分支表示本地分支默认对应哪个远程分支。
- **在本项目中**：本地 `codex/mvp-foundation` 跟踪 `origin/codex/mvp-foundation`，两边一致表示已提交内容也已经推送到 GitHub。
- **别混淆**：跟踪关系只说明两条分支怎样对应，不表示它们已经合并进 `main`。

### Working Tree（工作区）

- **一句话**：你当前在文件夹里实际看见和编辑的文件状态。
- **例子**：修改 `AGENTS.md` 后但还没 Commit，这个改动位于工作区。

### Tracked 与 Untracked（已跟踪与未跟踪）

- **一句话**：已跟踪文件已经进入 Git 管理；未跟踪文件存在于文件夹，但 Git 还没有把它纳入历史。
- **在本项目中**：根目录 `handoff.md` 当前是未跟踪文件。

### Staging / Staged（暂存区 / 已暂存）

- **一句话**：暂存区是下一次 Commit 准备包含哪些变化的清单。
- **类比**：工作区是书桌，暂存区是准备装箱的物品，Commit 是封箱并贴上标签。

### Commit（提交）

- **一句话**：一次带说明和唯一编号的 Git 历史快照。
- **例子**：一次完成 Grove 生成基础链路的 Commit，可以作为后续编辑功能的起点。
- **别混淆**：Commit 只保存到本地历史；Push 才把它送到远程。

### Hash / Checksum（哈希 / 校验值）

- **一句话**：根据一份内容计算出的短编号或长字符串；内容改变，计算结果通常也会改变。
- **在本项目中**：Git 用哈希标识 Commit；同步交接文档时也可以比较两份文件的哈希，确认字节内容完全一致。
- **别混淆**：哈希适合识别和校验内容，不是用来阅读文件正文的密码。

### Branch（分支）

- **一句话**：从某个历史点长出的独立修改路线。
- **在本项目中**：技术实验保留在 `codex/prototype-open-design-grapesjs`；正式开发正在 `codex/mvp-foundation` 上进行。
- **为什么重要**：实验失败不会直接破坏稳定的 `main`。

### Baseline / Baseline Commit（基线 / 基线提交）

- **一句话**：大家同意下一项工作从哪个已经保存的版本继续。
- **在本项目中**：Issue #3 以已完成 Issue #2 的正式开发版本为基线，表示先拥有生成基础，再开始编辑和保存。
- **别混淆**：基线不一定是 `main`，也不表示基线之后不能继续产生新 Commit。

### main（主分支）

- **一句话**：通常代表当前正式、稳定基线的主要分支。
- **别混淆**：`main` 不是所有实验代码都应该直接修改的地方。

### checkout / switch（切换分支）

- **一句话**：让工作区切换到另一条分支或某个历史版本。
- **风险**：如果当前存在未提交改动，切换可能被阻止或把理解变复杂；先检查状态。

### Detached HEAD（游离 HEAD）

- **一句话**：当前查看的是某个 Commit，而不是站在一个分支上继续工作。
- **类比**：像翻到历史相册中的某一页，但没有进入任何正在续写的相册。
- **风险**：此时新 Commit 不属于普通分支，容易在切换后找不到。

### Push（推送）

- **一句话**：把本地分支的新 Commit 上传到远程仓库。
- **别混淆**：Push 不会自动合并到 `main`；它只更新指定远程分支。

### Worktree（工作树）

- **一句话**：让同一个仓库在电脑上同时拥有多个独立文件夹，每个文件夹可以检出不同的分支，互不影响。
- **在本项目中**：UI 改造在 `G:\AITOOLS\NEW-DESIGN-UI` 这个独立 worktree 中进行，原工作区的未提交内容保持原样，两边互不干扰。
- **别混淆**：worktree 之间共享同一份仓库历史，但工作区文件完全独立；在一个 worktree 提交不会改变另一个 worktree 的文件。

### Fetch 与 Pull（获取与拉取）

- **一句话**：Fetch 只获取远程最新信息；Pull 获取后还会尝试把变化合入当前分支。
- **风险区别**：Fetch 更偏只读检查；Pull 会改变当前分支内容。

### Merge（合并）与 Conflict（冲突）

- **一句话**：Merge 把两条分支历史合在一起；Conflict 是 Git 无法判断同一位置该保留哪一份修改。
- **例子**：两条分支同时修改同一段 `AGENTS.md`，合并时可能产生冲突，需要人或 Agent 选择正确内容。

### Pull Request / PR（合并请求）

- **一句话**：在 GitHub 上请求审查并把一个分支合入另一个分支的工作页面。
- **别混淆**：Push 分支不等于创建 PR；PR 也不等于已经合并。

### `.gitignore`

- **一句话**：告诉 Git 哪些尚未跟踪的文件或目录通常不应加入版本历史。
- **例子**：`node_modules/` 和本地运行数据适合忽略。
- **常见误解**：`.gitignore` 自己应该被跟踪；它也不会自动删除已经跟踪的旧文件。

### Discard（丢弃改动）

- **一句话**：放弃尚未提交的文件修改，让文件回到某个已保存状态。
- **风险**：通常会直接丢失工作区内容，很难恢复；没有明确授权不要执行。

### Reset（重置）

- **一句话**：移动 Git 当前历史指针，并根据参数选择是否同时改变暂存区或工作区。
- **为什么复杂**：`--soft`、默认 mixed 和 `--hard` 影响不同；`--hard` 会丢失本地改动。
- **类比**：不仅翻回旧存档，还可能把书桌上的未存档草稿一起清空。

### Revert（反向提交）

- **一句话**：新增一个 Commit，用相反修改抵消旧 Commit，而不是改写已经存在的历史。
- **适用场景**：错误 Commit 已经推送并被别人看见时，Revert 通常比 Reset 更安全。

### Reset、Revert 与 Discard 的区别

| 操作 | 主要影响 | 是否保留历史痕迹 | 常见风险 |
| --- | --- | --- | --- |
| Discard | 未提交的文件改动 | 不产生新历史 | 本地草稿直接丢失 |
| Reset | 分支指针、暂存区，可能还有工作区 | 可能改写本地历史 | 参数选错会丢改动 |
| Revert | 已有 Commit 的效果 | 产生一个新的反向 Commit | 历史变长，但较安全 |

## 四、AI、Agent 与 Codex

### Agent（智能代理）

- **一句话**：能读取上下文、制定步骤、调用工具、检查结果并继续执行的 AI 助手。
- **别混淆**：普通聊天模型只回答一段话；Agent 还能读文件、改代码、运行测试或操作 Issue Tracker。

### Skill（技能）

- **一句话**：给 Agent 的可复用工作流程和规则说明。
- **在本项目中**：`to-spec` 规定怎样生成正式 Spec，`handoff` 规定怎样写交接，`domain-modeling` 规定怎样维护产品语言。

### CLI（Command-Line Interface，命令行界面）与 Codex CLI

- **一句话**：CLI 是通过文字命令操作程序的方式；Codex CLI 是在终端中运行 Codex Agent 的工具。
- **在本项目中**：应用在后台调用已经安装并登录的 Codex CLI，用户不需要自己输入命令。

### Prompt（提示词）

- **一句话**：给模型的任务说明、背景、约束和输出要求。
- **例子**：模板提示会要求 Codex 保留特定视觉体系、不要追问，并输出完整 HTML。

### Model（模型）

- **一句话**：真正进行语言理解、推理和生成的 AI 系统版本。
- **别混淆**：Codex 是产品/Agent 工具；模型是 Codex 内部调用的智能核心。

### Token

- **一句话**：模型读取和生成内容时使用的计量单位，不等于一个汉字、一个单词或一元钱。
- **在本项目中**：完整 12 页 HTML 包含大量标签、CSS 和脚本，因此输出 Token 较多。

### Input、Cached Input、Output 与 Reasoning Token

| 类型 | 白话解释 |
| --- | --- |
| Input Token | 模型这一步需要读取的内容 |
| Cached Input Token | 与之前重复并命中缓存的输入部分 |
| Output Token | 模型最终生成的可见或机器可读内容 |
| Reasoning Token | 模型为完成复杂任务进行内部推理所用的部分 |

- **注意**：累计 Input 很高不表示全部是新的，也不能直接换算为账单金额。

### Context 与 Context Window（上下文与上下文窗口）

- **一句话**：上下文是模型当前能参考的所有信息；上下文窗口是一次能容纳的总量上限。
- **类比**：上下文像摊在桌面上的资料，上下文窗口像桌面大小。资料太多时，需要压缩、总结或丢掉噪声。

### Reasoning Effort（推理强度）

- **一句话**：模型在回答前愿意投入多少分析深度。
- **取舍**：强度高通常更慢、使用更多 Token，但复杂任务质量可能更好；强度低通常更快，但可能遗漏边界。

### 完整 HTML 生成契约（Full-HTML Generation Contract）

- **一句话**：Codex 每次返回包含页面、样式和脚本的一整份演示 HTML。
- **当前原因**：这条路线已经通过真实原型验证，最适合一周内展示。
- **代价**：模型需要反复读取和输出大量固定模板代码，耗时和 Token 较高。

### 结构化内容（Structured Content）

- **一句话**：Codex 只返回标题、正文、数据等固定字段，再由应用填进模板。
- **例子**：模型返回“第 1 页标题、正文、图片说明”，应用负责组合 CSS 和翻页脚本。
- **取舍**：通常更省 Token、更稳定，但需要先设计统一字段和模板填充逻辑。

### Artifact（成果制品）

- **一句话**：Agent 或构建流程产出的、可以被保存或继续使用的结果。
- **在本项目中**：完整 HTML、PDF 和 GrapesJS 项目数据都是不同用途的 Artifact。

### JSON、JSONL 与 NDJSON

- **一句话**：JSON 是带字段名的结构化文本；JSONL 和 NDJSON 都表示一行一个 JSON 事件，适合程序边生成边读取。
- **在本项目中**：Codex CLI 使用 JSONL 事件流报告任务开始、工具执行、完成和 Token 用量。

### Event Stream（事件流）

- **一句话**：程序运行时按发生顺序不断输出的一系列事件。
- **例子**：线程开始 → 生成开始 → 工具读取文件 → 生成完成 → 报告用量。

## 五、网页与编辑器

### Frontend 与 Backend（前端与后端）

- **一句话**：前端是浏览器里用户看见和操作的部分；后端在背后保存数据、调用 Codex 和导出 PDF。
- **别混淆**：按钮属于前端；按钮点击后执行的文件保存可能属于后端。

### API（Application Programming Interface，应用程序接口）

- **一句话**：两个程序部分按照约定互相请求和返回数据的入口。
- **例子**：前端发送“开始生成”，后端返回生成阶段和最终结果。

### HTML、CSS 与 JavaScript

| 技术 | 白话解释 | 在演示中的作用 |
| --- | --- | --- |
| HTML | 页面里有什么 | 标题、正文、图片和幻灯片结构 |
| CSS | 这些内容长什么样、放在哪里 | 字体、颜色、尺寸、布局和动画 |
| JavaScript | 页面怎样响应操作 | 翻页、键盘控制和动态行为 |

### 响应式布局（Responsive Layout）

- **一句话**：同一套页面根据屏幕宽度自动重新排列，而不是为每种设备单独做一个版本。
- **在本项目中**：左侧栏在窄屏收起成图标栏或顶栏、项目卡片列数自动减少、新建页从双栏变单栏，都是响应式布局；功能本身没有增加或减少。
- **别混淆**：响应式是“同一功能的重新排列”，不是“手机版新功能”。

### 流式布局与自由定位（Flow Layout 与 Absolute Positioning）

- **一句话**：流式布局是元素像文字一样按顺序自动往下排、一个挪走后面的会补上来；自由定位是元素被钉在页面上的固定坐标，挪走后原地留空。
- **在本项目中**：模板页面天然是流式布局；拖拽可编辑文字时会把文本框转成自由定位，并按「原位留白」约定在原位置保留空白（见 [`CONTEXT.md`](../CONTEXT.md) 正式定义），像 PPT 一样自由排版。
- **别混淆**：自由定位后挪走的元素不会让周围内容自动“回填”，这是访谈中用户拍板的行为，不是排版缺陷。

### DOM（Document Object Model，文档对象模型）

- **一句话**：浏览器把 HTML 解析成的一棵可被程序读取和修改的元素树。
- **例子**：一页幻灯片下面有标题、正文和图片，就像文件夹里有三个子项目。
- **在本项目中**：GrapesJS 操作 DOM 中被允许编辑的文字和普通图片。

### Element、Attribute 与 Class（元素、属性与类名）

- **一句话**：元素是页面对象，属性是对象携带的信息，Class 是一组用于样式或识别的标签名。
- **例子**：`<img>` 是图片元素，`src` 是图片来源属性，`editable-image` 可以是识别可编辑图片的 Class。

### `<img>` 与 SVG

- **一句话**：`<img>` 是普通图片元素；SVG 是用形状和路径描述的矢量图形。
- **在本项目中**：首周只编辑普通 `<img>` 内容图片，不编辑 SVG、Logo 和模板装饰。

### iframe

- **一句话**：在一个网页中嵌入另一个相对隔离网页的容器。
- **在本项目中**：可以用 iframe 隔离生成的演示 HTML，减少它直接影响主应用的机会。

### Canvas（画布）

- **一句话**：编辑器中放置和操作内容的主要可视区域。
- **别混淆**：这里的画布是界面概念，不一定指 HTML 的 `<canvas>` 绘图元素。

### GrapesJS

- **一句话**：一个在浏览器中编辑 HTML 结构和样式的开源编辑器框架。
- **在本项目中**：它负责文字选择、样式修改、图片拖动缩放、撤销/重做和项目状态保存。

### State 与 Persistence（状态与持久化）

- **一句话**：状态是产品此刻的数据和界面情况；持久化是把状态写到本地，使关闭或重新打开后仍然存在。
- **例子**：图片当前位于 `(55, 21)` 是状态；保存后重新打开仍在这个位置，说明状态被持久化。

### HTTP 状态码（HTTP Status Code）

- **一句话**：网页请求得到响应时附带的三位数结果编号，200 开头表示成功，400 开头表示请求有问题，500 开头表示服务器出错。
- **在本项目中**：导入上传通过检查返回 200；文件被判定「暂不支持」（包括类型不符、超过 10 MB 大小上限）返回 422，并在响应里附上完整的导入检查报告。
- **别混淆**：状态码是给程序看的信号，用户看到的是根据状态码渲染出的中文提示。

### 自包含 HTML（Self-contained HTML）

- **一句话**：打开一个 HTML 文件时，所需样式、脚本和关键资源尽量包含在文件自身，不依赖本机项目目录。
- **好处**：更容易复制、分享和独立打开。
- **在本项目中**：生成项目导出的 HTML 是自包含的；导入项目导出的 HTML 经过导出放宽，允许保留 https 图片链接，因此不追求完全自包含（但仍然禁止脚本和本地 file:// 引用）。

### 静态翻页（Static Paging）

- **一句话**：不靠任何脚本、只用浏览器自带滚动吸附实现的逐页翻页。
- **类比**：像幻灯片每页占满一屏，滚动一下就“啪”地吸附到下一页，页码印死在页面上。
- **在本项目中**：导入项目导出的 HTML 不含脚本，由产品注入的样式和页码徽章实现离线逐页翻阅；生成项目导出仍用原来的翻页方式。

### Sandbox 与安全预览（沙箱 / Safe Preview）

- **一句话**：把不完全可信的 HTML 放进权限受限的环境中运行。
- **类比**：像让访客在带门禁的会客室活动，而不是给他整栋楼的钥匙。
- **在本项目中**：允许翻页和动画，但阻止本地文件访问、主页面跳转、新窗口、表单、下载和外部 API。

### 内容安全策略（Content Security Policy / CSP）

- **一句话**：由网页声明“可以加载什么、可以连接到哪里”的浏览器安全规则。
- **在本项目中**：安全预览允许内嵌脚本、样式和合格图片，但用 CSP 阻止生成 HTML 向外部接口发送数据或加载外部脚本。
- **别混淆**：iframe 沙箱限制嵌入页面拥有哪些权限；CSP 限制页面能够加载和连接哪些资源，两者一起使用。

### Content-Type 与 MIME 类型（Content-Type / MIME Type）

- **一句话**：数据在网上传输时标注“我是什么类型的文件”的字段，例如 `text/html` 表示网页、`image/png` 表示图片。
- **在本项目中**：浏览器把 HTML 文件上传给本机后端时，会用 `Content-Type: text/html` 说明传的是网页文件，后端据此解析。
- **别混淆**：文件扩展名（.html）只是名字后缀；Content-Type 是传输时声明的类型，两者可以不一致，安全检查要两个都看。

## 六、测试与质量

### 测试驱动开发（Test-Driven Development / TDD）

- **一句话**：先写一个能说明用户期望、但因为功能尚未实现而失败的测试，再补最少实现让它通过。
- **在本项目中**：先让浏览器测试从首页寻找正式服务器并失败，再实现首页、新建、Grove 生成和安全预览，直到同一测试通过。
- **别混淆**：TDD 不是一次把所有测试写完；它是“一个失败测试 → 一小段实现 → 测试通过”的短循环。

### Test Seam（测试缝 / 测试入口）

- **一句话**：从系统的哪个边界输入操作并观察结果。
- **在本项目中**：主要测试入口是浏览器中的本地应用，而不是分别测试大量内部函数。
- **为什么重要**：测试入口越接近真实用户，越能证明整条链路组合后可用。

### Black-box Test（黑盒测试）

- **一句话**：只通过输入和可见结果判断产品，不依赖内部实现细节。
- **例子**：点击保存后回到首页再重新打开，检查内容是否恢复；不检查内部函数叫什么。

### Fixture（固定测试材料）

- **一句话**：为了让测试可重复而预先准备的固定输入或输出。
- **在本项目中**：日常测试使用固定 HTML 结果，避免每次真实调用 Codex。

### Replay Test（回放测试）

- **一句话**：把以前真实产生并保存的结果重新送进同一条产品流程，检查后续处理有没有坏。
- **在本项目中**：真实 Grove HTML 已经生成过一次；回放测试复用它检查兼容处理和安全预览，不再次消耗一次真实 Codex 生成。
- **别混淆**：回放能验证真实结果的后续处理，但不能代替所有新的真实生成验收。

### Fake 与 Mock（替身与模拟对象）

- **一句话**：测试中暂时代替真实外部系统的可控实现。
- **简单区分**：Fake 通常能提供简化但可运行的行为；Mock 更关注某个调用是否按预期发生。
- **在本项目中**：固定生成适配器可以作为 Codex 的 Fake。

### Deterministic / Non-deterministic（确定性 / 非确定性）

- **一句话**：相同输入总得到相同结果叫确定性；结果可能变化叫非确定性。
- **在本项目中**：固定 Fixture 是确定的；真实 Codex 文案和布局细节可能每次不同。

### 纯函数（Pure Function）

- **一句话**：只依赖输入参数、不改外面任何东西的函数；同样输入永远得到同样输出。
- **在本项目中**：导入检查器是一个纯函数缝——HTML 字符串进，判定档位、报告和处理后的 HTML 出，不碰文件和网络，所以能用固定样本反复测试。
- **别混淆**：纯函数 ≠ 确定性测试；但纯函数是写出确定性测试的好帮手。

### E2E / End-to-End Test（端到端测试）

- **一句话**：从用户入口走到最终结果，验证界面、后端、保存和导出组合后能工作。
- **例子**：新建 → 发送 → 编辑 → 保存 → 重新打开 → 导出 PDF。

### Smoke Test（冒烟测试）

- **一句话**：快速检查最关键功能是否基本可用。
- **类比**：机器开机先看有没有冒烟；不是全面体检。
- **在本项目中**：五个模板各跑一次生成、简单编辑和导出属于资格冒烟检查。

### Acceptance Test（验收测试）

- **一句话**：按照验收标准证明产品是否达到交付要求。
- **在本项目中**：最终用真实材料和真实 Codex 跑完整演示是验收测试。

### Regression Test（回归测试）

- **一句话**：修改新功能后重新检查旧功能，防止原本可用的地方被破坏。
- **例子**：增加第二个模板后，还要重新确认 Grove 的保存和导出没有坏。

### Playwright

- **一句话**：自动控制真实浏览器进行点击、输入、截图和结果检查的工具。
- **在本项目中**：原型已用它验证图片拖动、撤销/重做、HTML 翻页和 PDF 输出。

### Flaky Test（不稳定测试）

- **一句话**：代码没变，但测试有时通过、有时失败。
- **常见原因**：等待时间不正确、网络波动、依赖真实 AI 随机输出或元素定位不稳定。
- **解决方向**：例行测试使用 Fixture，并等待明确状态而不是固定睡眠。

## 七、运行、依赖与导出

### Node.js

- **一句话**：让 JavaScript 可以在浏览器之外运行的环境。
- **在本项目中**：本地后端和原型服务器使用 Node.js。

### pnpm、Package 与 Dependency（包管理器、软件包与依赖）

- **一句话**：软件包是可复用代码；依赖是项目需要的外部软件包；pnpm 负责安装和管理它们。
- **例子**：GrapesJS、Express 和 Playwright 都是项目依赖。

### `package.json`

- **一句话**：Node.js 项目的基础清单，记录项目脚本、名称和依赖。
- **例子**：`pnpm start` 启动正式本地应用，`pnpm test:browser` 运行浏览器测试，这些命令都在清单中定义。

### Server、localhost 与 Port（服务器、本机地址与端口）

- **一句话**：Server 接收请求并返回内容；localhost 表示当前电脑；Port 像同一台电脑上不同服务的门牌号。
- **在本项目中**：`127.0.0.1:4318` 表示 AI Presentation Studio 只在当前电脑访问，端口号为 4318。

### 数据目录（Data directory）

- **一句话**：应用专门用来保存项目状态和运行数据的文件夹。
- **在本项目中**：正式演示验收使用 Issue #7 worktree 下的独立数据目录，不读取或覆盖用户原工作区的 `.app-data`。
- **别混淆**：数据目录保存可重新打开的项目状态；导出的 HTML 和 PDF 是交付成果，不是项目恢复格式。

### 只读副本（Read-only Copy）

- **一句话**：把原文件原样复制一份保存，之后只拿它来查看，不再修改。
- **在本项目中**：导入演示时，上传的原始 HTML 文件会先存一份只读副本放在数据目录里；编辑只改动应用内部的项目记录，原始文件和它的副本都保持上传时的字节内容不变。
- **别混淆**：只读副本不是备份恢复点；删除导入项目时，应用会把这个副本一并删除。

### Windows 启动脚本（Batch File / `.cmd`）

- **一句话**：可以在 Windows 中双击执行的一组启动命令。
- **在本项目中**：双击 `start-ai-presentation-studio.cmd` 会启动本地后端并自动打开项目页面；关闭承载后端的命令窗口后应用停止。
- **别混淆**：`.cmd` 文件是启动入口，不是安装包，应用仍然从当前项目目录运行。

### Process 与 Child Process（进程与子进程）

- **一句话**：进程是正在运行的程序实例；子进程是一个程序启动的另一个程序。
- **在本项目中**：本地后端是进程，它启动 Codex CLI 作为子进程。

### stdin、stdout 与 stderr

- **一句话**：stdin 是程序接收文字输入的通道；stdout 是正常输出；stderr 是进度或错误输出。
- **在本项目中**：生成提示通过 stdin 发送给 Codex，JSON 事件从输出通道读取。

### Exit Code（退出码）

- **一句话**：程序结束时返回的数字，通常 `0` 表示成功，非 `0` 表示发生错误或被中断。
- **注意**：退出码只说明结果状态，具体原因仍要看日志。

### Environment Variable（环境变量）

- **一句话**：操作系统或启动命令提供给程序的配置值。
- **例子**：可以用环境变量告诉原型不要自动打开浏览器，而不修改代码。

### Validation 与 Compatibility Check（验证与兼容性检查）

- **一句话**：在使用生成结果前检查它是否满足必要结构和安全规则。
- **在本项目中**：检查完整 HTML、多页结构、可编辑图片标记、本地文件 URL 和禁止能力。
- **别混淆**：检查通过表示“产品暂时能处理”，不表示 HTML 在所有场景都完美安全或通用兼容。

### 启发式规则（Heuristic）

- **一句话**：凭经验特征的“经验法则”判断，不保证全对，但能快速给出够用的结论。
- **在本项目中**：导入检查靠一组启发式识别演示页面——比如 class 里带完整词 slide（或 slide-1 这类“slide + 编号”）的容器算一页、两个以上并列的 `<section>` 各算一页；规则按优先级执行，每条规则都有固定的正反样本测试。启发式可能漏判，所以兼容性声明只以样本集通过为准；真实样本测试还发现过把 `slide-content` 这类页内部件误判成页的问题，已按样本证据调优规则。
- **别混淆**：启发式不是精确解析；它宁可保守拒绝，也不把无法安全编辑的文件放进来。

### PDF Export（PDF 导出）

- **一句话**：把当前已保存演示通过浏览器渲染成分页 PDF 文件。
- **在本项目中**：后端控制本机 Chrome，一张幻灯片对应一页 PDF。

### License 与 Attribution（许可证与署名）

- **一句话**：许可证规定别人代码或模板可以怎样使用；署名是按要求说明原作者和来源。

## 九、产品经理求职与证据表达

### 求职证据库（Career Evidence Bank）

- **一句话**：持续保存“做过什么、为什么这样做、结果和证据是什么”的项目档案，未来用于简历、作品集和面试。
- **在本项目中**：[`docs/PM-CAREER-EVIDENCE.md`](PM-CAREER-EVIDENCE.md) 记录选题、假设、取舍、砍掉的范围、风险降低、指标和面试故事。
- **别混淆**：它不是流水账；只保留能说明产品判断、行动和结果的关键事件。

### 假设与验证（Hypothesis / Validation）

- **一句话**：假设是“目前认为可能成立”；验证是用原型、测试、访谈或数据检查它到底是否成立。
- **例子**：“GrapesJS 能编辑普通图片”最初是假设；真实完成拖动、缩放和恢复后，才成为有边界的已验证结论。
- **别混淆**：决定采用一个方案，不等于已经证明它能带来用户价值。

### 证据边界（Evidence Boundary）

- **一句话**：现有证据最多支持一句话说到什么程度。
- **例子**：只验证 Grove，就能说“Grove 原型跑通”，不能说“5 个模板都稳定可用”。
- **作用**：防止简历把计划写成完成、把一次成功写成稳定能力、把技术结果写成业务结果。

### Claim Status（证据状态）

- **一句话**：给证据库中的判断贴上“已经证明、只是决定、仍是假设或以后再做”等状态，防止说过头。
- **常用状态**：`VERIFIED` 是已有证据；`DECIDED` 是已经拍板但结果未验证；`HYPOTHESIS` 是待验证假设；`PLANNED` 是未来计划；`DEFERRED` 是主动暂缓；`REJECTED` 是明确不采用或已被证据否定。
- **别混淆**：决定做一件事只能标为 `DECIDED` 或 `PLANNED`；必须出现真实文件、测试、用户反馈或数据，才能把对应结果标为 `VERIFIED`。

### 产品取舍（Product Tradeoff）

- **一句话**：面对不能同时满足的目标，明确优先什么、放弃什么，并说明理由和代价。
- **例子**：首周选择完整 HTML 来加快交付，同时接受生成较慢和 Token 较多的代价。
- **别混淆**：取舍不是随意删功能，而是根据目标、时间和风险作出可解释选择。

### 风险降低（Risk Reduction）

- **一句话**：先找出最可能让项目失败的不确定性，用尽量低成本的方法获得证据。
- **例子**：正式开发前先做 Open Design + Codex + GrapesJS 技术原型，比做完全部页面后才发现编辑链路不可行，损失更小。

### 指标与基线（Metric / Baseline）

- **一句话**：指标是用来观察结果的数字；基线是改进前的对照数字。
- **例子**：要证明“节省制作时间”，必须先记录旧流程需要多久，再记录新流程需要多久；只有新流程时间，没有基线就不能计算提升比例。
- **别混淆**：页数、Token 和运行时间是技术诊断指标，不自动等于用户价值或业务效果。

### STAR 面试表达

- **一句话**：按 Situation（背景）、Task（任务）、Action（行动）、Result（结果）讲清一段经历。
- **重点**：Action 要说明你具体如何判断和推进；Result 必须有证据，也可以是“降低了关键不确定性”，不必强行编造增长数据。
- **在本项目中**：证据库已经整理了范围收窄、完整 HTML 取舍、暂缓 HTML 导入、技术原型验证和正式纵向交付五类故事。
