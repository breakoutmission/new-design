# AI Presentation Studio 产品经理求职证据库

更新时间：2026-07-16
维护方式：由本仓库中的后续 Agent 按 [`docs/agents/pm-career-evidence.md`](agents/pm-career-evidence.md) 持续维护

## 这份文档有什么用

这不是普通开发日志，而是为产品经理实习求职准备的“证据库”：把项目中真正体现产品经理价值的思考、决定、验证和结果保存下来，未来用于简历、作品集和面试。

它重点回答六个问题：

1. 为什么选择这个项目？
2. 用户问题是什么，为什么值得解决？
3. 哪些判断一开始只是“假设”，后来怎样验证？
4. 做过哪些范围取舍，主动砍掉了什么，为什么？
5. 怎样把高风险问题提前暴露，并一步步降低失败风险？
6. 用户本人具体做了什么，Agent 和工具又完成了什么？

## 证据边界

“证据边界”就是：一句话最多能说到什么程度，由现有证据决定。

| 状态 | 白话解释 | 能不能写成已完成成果 |
| --- | --- | --- |
| `VERIFIED` 已验证 | 有原型、测试、文件、Issue、Commit、用户反馈或数据支持 | 可以，但必须保留限制 |
| `DECIDED` 已决定 | 已经拍板并留下记录，用户结果尚未验证 | 只能写“定义/决定/规划”，不能写“取得效果” |
| `HYPOTHESIS` 假设 | 目前认为可能成立，仍需验证 | 不可以 |
| `PLANNED` 计划 | 准备做但还没做 | 不可以 |
| `DEFERRED` 暂缓 | 为控制范围或风险而主动延后 | 可以作为取舍来讲 |
| `REJECTED` 否定 | 已明确不采用，或证据不支持 | 可以作为学习和取舍来讲 |

本项目目前不能声称“节省了多少时间”“有多少真实用户”“提高了多少满意度或转化率”。这些指标还没有测试。能诚实讲清楚“验证了什么、还没验证什么”，本身就是产品经理的重要能力。

## 一、为什么选择这个项目

### 项目出发点

- **VERIFIED**：这是用户为了求职产品经理实习而发起的真实项目实践，不是为了堆功能或模仿一个现成产品。
- **VERIFIED**：首个用户就是产品作者本人——不懂 HTML/CSS，但需要把中文产品项目材料做成可以继续编辑和交付的演示文稿。这个首个场景已经写入 [`CONTEXT.md`](../CONTEXT.md)。
- **DECIDED**：首个版本只解决一条完整链路：粘贴中文材料 → 选择模板 → AI 生成 → 轻量编辑 → 保存并重新打开 → 导出 HTML/PDF。

### 这个选题为什么适合展示产品经理能力

1. **问题来自真实使用场景**：产品作者自己就是首个用户，可以提供真实材料并完成第一轮验收。
2. **价值链路可以完整演示**：不是只展示一个静态页面，而是从输入材料一直走到可交付成果。
3. **存在需要判断的真实矛盾**：速度与质量、通用性与一周交付、模型自由度与格式稳定性、功能丰富度与首版风险之间都需要做取舍。
4. **适合用证据推进**：Open Design、Codex 和 GrapesJS 能组合成可测试的技术链路，高风险问题可以先用原型验证。
5. **能展示“把模糊问题变清楚”**：项目已经把大量口头讨论沉淀为领域语言、ADR、正式 Spec、子任务和验收标准。

### 尚未证明的选题假设

- **HYPOTHESIS**：除了产品作者本人，还有一批不懂 HTML/CSS、需要把中文材料制作成演示文稿的人愿意使用这个产品。
- **HYPOTHESIS**：相比现有工具，这条流程能显著减少制作时间或返工。
- **HYPOTHESIS**：5 个预设模板足以覆盖首批用户的视觉偏好。

这些问题需要后续用访谈、任务测试和真实使用数据验证，当前不能当作市场结论。

## 二、30 秒项目叙述

我以自己准备产品经理求职材料时的演示文稿制作需求为首个真实场景，把一个较宽泛的 AI 演示编辑器想法收敛为一周可展示的本地 MVP。过程中，我持续明确用户、核心链路和验收标准，主动砍掉聊天、文件上传、任意 HTML 导入、PPTX 等首周非核心能力；同时驱动 Agent 用 Open Design、Codex 和 GrapesJS 搭建技术原型，优先验证生成、编辑、保存恢复及 HTML/PDF 导出的最高风险链路。根据原型证据，我选择首周先采用完整 HTML 生成，并把代价、限制和后续优化条件写入 ADR，再拆成可执行的 GitHub Issues 进入正式开发。

> 这段是当前版本的面试开场，不是最终简历正文。后续获得真实用户和效果数据后应继续更新。

## 五、关键取舍与为什么

### 1. 完整 HTML vs. 结构化内容

- **不确定性**：让 Codex 每次返回整个 HTML，集成最快但慢且耗 Token；只返回结构化内容更稳定，但必须先设计统一数据格式和模板填充系统。
- **行动**：先用 Grove 做完整 HTML 技术原型，实际生成、编辑、保存和导出。
- **决定**：一周 MVP 使用完整 HTML；浏览器日常测试使用固定夹具，真实 Codex 只用于模板资格验收和最终真实材料演示。
- **为什么**：首周目标是尽快证明完整链路，而不是提前解决长期架构的全部问题。
- **代价**：一次原型运行约 3 分 45 秒，Token 较多，并可能出现模型输出结构漂移。
- **降低的风险**：避免首周同时发明结构化格式、模板填充器和兼容迁移方案。
- **证据**：[ADR-0012](adr/0012-use-full-html-generation-for-one-week-mvp.md)。

### 2. 完整复用 Open Design vs. 选择性复用

- **不确定性**：直接基于整个仓库开发可能更快获得现成功能，也可能把无关复杂度和历史约束带入首版。
- **决定**：只复用 zhangzara 模板及许可证信息，编辑能力由 GrapesJS 承担，不整体合并 THROWAWAY 原型分支。
- **降低的风险**：缩小需要理解、修改和维护的代码范围，同时保留模板视觉资产。
- **证据**：[ADR-0010](adr/0010-selective-open-design-reuse-with-grapesjs.md)、正式开发 Commit [`471a980`](https://github.com/breakoutmission/new-design/commit/471a980)。

### 3. 通用 HTML 导入 vs. 首周完整主链路

- **不确定性**：导入任何 HTML 看起来有吸引力，但不同结构、脚本和资源会带来兼容与安全问题。
- **决定**：保留未来“能力检查”的产品方向，但首周完全暂缓导入，先完成生成项目的编辑、保存和导出。
- **降低的风险**：避免为了边缘入口拖慢主链路；也避免不兼容文件被强行打开后损坏。
- **证据**：[ADR-0002](adr/0002-capability-based-html-imports.md)、[ADR-0009](adr/0009-defer-arbitrary-html-import-for-one-week-mvp.md)。

### 4. 一次做完 5 个模板 vs. Grove 纵向切片

“纵向切片”是先让一个模板从头到尾可用，而不是先把所有模板的某一小段一起做完。

- **决定**：Grove 先打通启动、生成、预览、编辑、保存和导出，再让其余 4 个模板逐一通过资格验收。
- **降低的风险**：最早暴露各模块组合问题，并尽快获得可展示成果。
- **当前进展**：正式分支已完成 Grove 的启动、生成、安全预览、编辑、保存、重新打开、失败/取消恢复、单生成任务限制，以及删除和重新生成确认；用户对 Issue #3 的人工复验暴露真实 CSS 保真缺口后，回归 Bug #8 已修复并关闭。Issue #5 已在独立 worktree 从共同基线 `4a3f822` 完成正式 HTML/PDF 导出验收并关闭，提交为 `e70bfca`；其余 4 个模板和真实材料完整演示仍未完成。
- **证据**：[Issue #2](https://github.com/breakoutmission/new-design/issues/2)、[Issue #3](https://github.com/breakoutmission/new-design/issues/3)、[Issue #4](https://github.com/breakoutmission/new-design/issues/4)、[Issue #5](https://github.com/breakoutmission/new-design/issues/5)、[Issue #8](https://github.com/breakoutmission/new-design/issues/8)。

## 十、面试故事库

STAR 是一种面试表达结构：Situation（背景）、Task（任务）、Action（行动）、Result（结果）。结果必须是已经发生并可证明的结果，也可以包含“降低了什么不确定性”，不一定非要是增长数据。

### 故事 A：怎样把一个很大的想法收窄成一周 MVP

- **S 背景**：最初想做基于 Open Design 的 AI 演示产品，可能包含模板、聊天、导入和完整编辑等大量能力。
- **T 任务**：作为第一次做产品项目的实践，需要在一周内完成可展示、可解释、可验收的版本。
- **A 行动**：先明确首个用户和单一场景，再逐项确认输入、生成、编辑、保存和导出边界；每增加一个功能都追问它是否直接服务完整主链路，并记录范围外内容。
- **R 结果**：形成一个端到端一周 MVP，暂缓上传、聊天、任意 HTML 导入、PPTX 等能力，并把范围写入正式文档和 Spec，使开发可以按纵向子任务推进。
- **体现能力**：问题定义、优先级、范围管理、沟通对齐。

### 故事 B：怎样在完整 HTML 和结构化内容之间做决定

- **S 背景**：完整 HTML 能保留模板效果并快速集成，但生成慢、Token 多、输出可能漂移；结构化内容更稳定，却需要先设计新格式和模板填充系统。
- **T 任务**：不能靠偏好决定，需要选出最适合一周 MVP 的路线。
- **A 行动**：驱动 Agent 先用 Grove 运行真实 Codex 原型，测量生成时间和 Token，并验证后续编辑、保存和导出是否真的能工作。
- **R 结果**：原型完整跑通，证明首周路线可行；同时发现一次生成约 3 分 45 秒和较高 Token 成本。因此决定首周用完整 HTML、日常测试使用固定夹具，并把结构化内容保留为 MVP 后的优化方向。
- **体现能力**：数据辅助决策、阶段性取舍、技术理解、风险意识。

### 故事 C：为什么主动砍掉任意 HTML 导入

- **S 背景**：导入本地 HTML 对用户有吸引力，但“任何 HTML”在结构、脚本和资源上差异很大。
- **T 任务**：既不能把产品说成“只支持自家 5 个模板”，也不能在没有验证时承诺通用兼容。
- **A 行动**：先定义未来采用能力检查：兼容就打开，不兼容就明确提示；随后根据一周目标再次评估优先级。
- **R 结果**：保留了开放兼容的产品原则，但把导入整体暂缓到 MVP 之后，使首周资源集中于生成项目主链路，也避免强行打开不兼容 HTML 的安全和损坏风险。
- **体现能力**：用户价值与交付风险平衡、边界设计、敢于砍功能。

### 故事 D：怎样用原型降低正式开发风险

- **S 背景**：Open Design 模板、Codex 输出、GrapesJS 编辑和 Chrome PDF 导出跨越多个系统，任何一段失败都会推翻方案。
- **T 任务**：在正式开发投入之前，找出方案是否真正可行以及最危险的限制。
- **A 行动**：建立可丢弃的技术原型，逐项验证 12 页加载、文字编辑、图片拖动与等比缩放、撤销重做、项目数据恢复、独立 HTML 翻页和 PDF 导出。
- **R 结果**：关键链路得到验证，同时提前发现图片占位、Windows Codex 启动、Chrome 权限、图片覆盖点击和生成成本问题；这些发现进入正式决策与验收边界。
- **体现能力**：假设拆解、实验设计、风险前置、从失败可能性反推验证顺序。

### 故事 E：怎样把一份大 Spec 变成可以连续交付的工作

- **S 背景**：父 Spec 包含 71 条用户故事，如果按前端、后端、编辑器分别开工，很难判断什么时候出现第一个真正可用结果。
- **T 任务**：把正式 Spec 变成 Agent 可以独立接手、用户可以逐段验收、失败时影响范围有限的开发计划。
- **A 行动**：要求先展示拆分粒度和依赖再发布；按用户可见链路拆成 6 个子 Issue，并坚持先 Grove、后其他模板，先固定结果自动测试、再做真实 Codex 验收。
- **R 结果**：Issue #2、#3、#4 和 #5 已分别用提交 `471a980`、`1164d76`、`4a3f822`、`e70bfca` 和公开浏览器测试完成闭环；正式 Grove 链路已经覆盖启动、生成、安全预览、编辑、保存、重新打开、失败/取消恢复、危险操作确认和 HTML/PDF 导出。其余 4 个模板与真实材料完整演示仍明确留在后续 Issue，未被提前包装成完成。
- **体现能力**：需求拆解、依赖管理、AI Agent 协作、验收设计、交付节奏与诚实边界。

### 故事 F：为什么“能编辑”还不等于“用户能继续工作”

- **S 背景**：技术原型已经证明 Grove 页面能被 GrapesJS 修改，但如果用户只能当场编辑，保存后无法恢复，核心链路仍然会在下一次打开时断掉。
- **T 任务**：把“编辑器功能存在”转化为一个可持续工作的正式产品切片，同时避免把背景、Logo、SVG、模板装饰和任意 HTML 都误开放为可编辑内容。
- **A 行动**：坚持默认先预览、用户主动点击后才进入编辑；用兼容标记限定普通内容图片，把其他元素保持锁定；要求保存以 GrapesJS 项目数据为准，并从该状态生成安全预览；用 TDD 先让公开界面测试在缺少“保存”时失败，再覆盖文字和图片修改、撤销/重做、保存提示、最后修改时间、返回首页、重新打开及新会话空历史。
- **R 结果**：Issue #3 的 10 项验收标准全部通过并关闭，提交 `1164d76` 将 Grove 正式链路推进到编辑、保存与重新打开；证据只支持 Grove 单模板和同一服务进程内的重开，不代表 5 个模板稳定、跨进程恢复或真实用户效率提升已经验证。
- **体现能力**：从用户任务定义验收、保存后继续工作的设计、范围控制、风险前置、AI Agent 协作和证据边界管理。

### 故事 G：为什么正常生成成功还不等于产品可以放心使用

- **S 背景**：正式链路已经能生成、编辑和保存，但如果生成失败留下残缺页面、取消按钮没有真正停掉 Codex，或删除与重新生成同时发生导致项目重新出现，用户仍不敢把真实材料交给产品。
- **T 任务**：把“偶尔成功”推进为失败后能够继续工作的产品流程，同时保护会永久删除或覆盖内容的操作。
- **A 行动**：把成功、取消、失败、一步重试、全局单生成任务限制、生成期间编辑其他项目、删除确认和重新生成确认写成 Issue #4 的公开界面标准；要求先出现失败测试，再实现；要求真实检查 Windows 上对应 Codex 进程树确实终止；对偶发测试使用根因诊断，并用固定基线的双路代码审查分别核对仓库规则和全部验收标准。
- **R 结果**：Issue #4 全部验收通过并关闭，提交 `4a3f822` 完成 Grove 的失败/取消恢复和受保护操作；Playwright 覆盖正常路径、跨页面冲突和完成阶段取消，真实 Codex 测试验证取消后对应进程树消失。证据仍只支持本地 Windows、Grove 单模板和所测场景，不能声称已经获得长期失败率或外部用户可靠性数据。
- **体现能力**：异常路径设计、数据安全意识、验收标准设计、跨页面冲突风险管理、AI Agent 协作和诚实的证据边界。

## 十一、用户与 Agent 的贡献边界

### 用户已经做出的产品贡献

- 明确这个项目首先服务产品经理实习求职实践，并以自己作为首个真实用户。

- 把讨论整理成领域文档、ADR、Spec、Issues、交接文档和维护规则。
- 编写技术原型与正式代码，运行浏览器、HTML、PDF 和状态恢复验证。

### 面试时怎样诚实表达

推荐说法：

> 我负责问题定义、范围取舍、验收标准和关键路线决策，并把 AI Agent 当作跨职能执行工具，驱动它完成文档、原型和测试；我根据实际证据持续纠偏和收窄方案。

不推荐说法：

> 我独立完成了全部产品设计和代码开发。

前一种说法更能体现 AI 时代产品经理的核心价值：不是亲自完成每一行代码，而是能定义正确问题、组织验证、作出取舍、控制风险并推动结果落地。
