> 用法：开新票前、做完一张票后，扫一眼这张卡。全部规则来自本仓库的真实实践。

**分支命名习惯**：`codex/<Issue编号>-<英文短名>`，一张票开一条新线，从「当时最新的基线」切出，完成后合回基线。票即分支，分支即票。

## 二、什么时候直接合并（merge），什么时候开 PR

先分清两个词：

- **合并（merge）**：把一条分支上的成果「接回」另一条分支的动作，git 一次操作完成。
- **PR（Pull Request，拉取请求）**：在 GitHub 上开的一张「申请单」——「我这条线做完了，请审查后允许合并」。它本质是**给合并动作加了一道公开的审查与讨论环节**。

### 决策规则（三条问题依次问自己）

1. **这次合并需要留下公开的审查讨论记录吗？**
   需要 → PR。比如：里程碑进入 `main`、拿不准的设计想让别人事后能看到讨论。
2. **质量证据已经沉淀在别处了吗？**
   本项目的票内流程（TDD 红绿循环 + 全套浏览器回归 + 双路代码审查 + Issue 验收评论）已经留下完整证据链 → 直接 merge 即可，证据在 Issue 里可查，不必再走 PR 形式。
3. **这次合并是「对外版本发布」级别的节点吗？**
   是（比如验收收尾票 #21 之后）→ PR 合入 `main`。只是票与票之间的日常接续 → 直接 merge 回基线。

### 本仓库的真实对照（两个都发生过）

| 真实事件 | 走的路 | 为什么 |
| --- | --- | --- |
| Issue #7 最终演示成果进入 `main` | **PR #10** | 里程碑级节点，PR 留下正式审查记录 |
| Issue #14 导入功能合回基线 | **直接 merge**（`32fcc26`、`838dcbc`） | 票内已有全套回归 + 双路审查 + Issue 验收评论；且仓库设定 PR 不进任务分诊，日常票不走 PR |

### 分叉教训（2026-08-29 的真实事故）

`codex/mvp-foundation` 本地线和远端线曾各自前进：远端合入了 #9 修复，本地压着未提交的 #11 界面重构，两条线分叉六周。结果：既不能干净合并，也一度只剩一个模板可看。**教训**：一张票的工作线要「从最新基线切出、尽快合回」；同一张票不要在两个目录各写一份不互通的代码。

## 三、一张票的标准生命周期（背下来）

```
① 从最新基线切出新分支      git switch -c codex/<票号>-<短名>   （基线 = codex/ui-open-design-reference 的最新 tip）
② 票内开发                  TDD 红绿循环，随时提交
③ 票内验收                  全套回归 + 双路审查 + Issue 验收评论 → 关闭 Issue
④ 合回基线并推送            在基线上 git merge --no-ff <票分支>，全套测试绿后 git push
⑤ （可选）删除票分支        已合并的票分支只是存档
⑥ 里程碑时（可选）          基线 → main 用 PR，给对外版本留审查记录
```

## 四、自测三题（先回忆再看答案）

1. 你做完 #16（编辑面板扩展）并验收关闭，应该直接 merge 还是开 PR？合到哪条分支？
2. `main` 现在落后于基线，什么时候才值得把基线合进去？
3. 为什么 #14 当时不合并回 `codex/mvp-foundation`？

<details><summary>答案</summary>

1. 直接 merge 回 `codex/ui-open-design-reference`——票内质量证据已沉淀在 Issue，日常票不走 PR（仓库设定 PR 不进分诊）。
2. 里程碑节点，比如 #21 真实样本验收收尾后，用 PR 给 `main` 留一次正式的版本记录。
3. 因为那条本地线和远端已经分叉（远端含 #9 修复、本地压着未提交内容），硬合并会产生冲突且有覆盖风险；正确做法是像当时那样以干净基线新建工作区。
