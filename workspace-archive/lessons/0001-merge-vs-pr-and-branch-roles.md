# 第 1 课：什么时候合并，什么时候开 PR，我的每条分支是干什么的

> 10 分钟读完。全部用你自己的仓库当例子——你刚经历完一次真实的合并（Issue #14），这正是最好的教材。
> 速查版在 [`reference/0001-git-merge-pr-branches.md`](../reference/0001-git-merge-pr-branches.md)，以后开票前扫一眼那张卡就够。

## 一、先把三个词说人话

- **分支（branch）**：平行草稿线。从主线上某个点复制出一个平行世界，随便改，不影响主线。就像你写 PPT 前先「另存为」一份副本再乱改。
- **合并（merge）**：把草稿线上改好的内容「接回」主线的动作。git 里的一个命令，几秒钟的事。
- **PR（Pull Request，拉取请求）**：在 GitHub 上开的一张「申请单」——「我这条草稿线做完了，请审查，同意后我再合并」。它不是另一种合并方式，而是**给合并加了一道公开的审查和讨论环节**。申请单上会留 Comments（评论，大家围绕改动写的讨论），事后可以查。

## 二、核心判断：只问三个问题

```
① 需要留下公开的审查讨论记录吗？
   需要（里程碑进 main、想让大家看到讨论）→ 开 PR
   不需要 ↓

② 质量证据已经沉淀在别处了吗？
   你的票内流程已有完整证据链（TDD 测试 + 全套回归 + 双路代码审查 + Issue 验收评论）
   → 直接 merge，证据去 Issue 里查

③ 这是「对外发版」级别的节点吗？
   是（比如 #21 收尾验收后）→ 基线 → main 走一次 PR
   只是票与票之间的日常接续 → 直接 merge 回基线
```

## 三、用你自己仓库的两个真实事件验证

**事件 A：PR #10**（Issue #7 最终演示成果进入 `main`）
走了 PR。因为那是里程碑节点——五模板资格验收后的正式演示收口，值得在 GitHub 上留一张正式申请单。

**事件 B：Issue #14**（导入演示最小链路合回基线）
直接 merge。因为票内已经做了：TDD 红绿循环 → 全套浏览器回归 16 条 PASS → 双路代码审查 → Issue 验收评论逐条对账。证据已经写进 Issue #14 的评论里，任何人点开就能查——再开一张 PR 重复审查，只是形式主义。而且这个仓库设定了 PR 不进任务分诊（PR 不当作工单处理），日常票一直走的是直接 merge。

**结论：你的仓库里，日常票 = 直接 merge 回基线；只有里程碑进 `main` 时才值得开 PR。**

## 四、你的每条分支是干什么的（当前现状）

把你仓库想成一家小公司：

| 分支 | 相当于 | 现状 |
| --- | --- | --- |
| `codex/ui-open-design-reference` @ `838dcbc` | **工作车间的主装配线** | 现役基线，全部最新成果在这。新票从它切出，做完合回它 |
| `codex/issue-14-import-foundation` | **刚用完的工作台** | #14 的票分支，内容已全部进基线，可删可留 |
| `codex/mvp-foundation`（本地） | **退休的旧装配线** | 老代码线，内容已被基线吸收，不再合并、别从它启动应用 |
| `main`（远端） | **对外的展厅** | 停在旧版本。里程碑时用 PR 把基线成果正式搬进展厅一次 |
| `codex/issue-5/6/7/9…` | **历史工单的档案柜** | 内容都已在基线里，当档案看 |

**记住一个命名规则**：`codex/<票号>-<英文短名>`——一张票一条线。票开线，票完线合，票即分支。

## 五、为什么当初 #14 没有合回 `mvp-foundation`（一个值得记住的事故）

你的仓库曾发生分叉（两条线各自前进、互不包含）：

- 远端的 `mvp-foundation` 合入了 #9 多页修复（7 月 18 日）
- 本地目录压着未提交的 #11 新界面（8 月）
- 两条线分叉了六周，结果：既不能干净合并，你打开应用还「只剩一个模板」

当时正确（也实际执行了）的处理：放弃硬合并，确认 `7dfde4b` 这条干净线（已同时包含 #9 和 #11），把 #14 建在它上面。旧线退役封存。

**教训一句话**：一张票从最新基线切出、做完尽快合回；不要让两条线各走各的超过几天。

## 六、动手练习（下次开票时照做）

下一次开 #16 或 #15 时，不要让 AI 代劳第一步，你自己说出这三句话：

1. 「从 `codex/ui-open-design-reference` 的最新 tip 切出分支 `codex/<票号>-<短名>`」
2. 「验收关闭后，把票分支 merge 回基线，全套测试绿了再 push」
3. 「不合回 `mvp-foundation`，也不动 `main`——`main` 留到 #21 后的里程碑」

能不看卡片说出这三句，这一课就学会了。
